## 1. 结论摘要

1. **可行**：`compio::runtime::spawn` 只要求 `F: Future + 'static`，**不要求 `Send`**
   （`compio-runtime-0.12.6/src/lib.rs:559`），因此「适配器内部 spawn 一个后台泵、
   `try_read` 不再手工 pump 一遍」这条路在 compio 上是成立的——这正是它和
   `buffex_tokio_adapt`（多线程 `tokio::spawn` 要求 `Send`，而环的 park future 无法被证明
   `Send`，只能改成按需驱动）的根本差别。
2. **代价（compio 固有）**：compio 的读写接口把 buffer **按值**传入、且要求
   `IoBufMut` / `IoBuf` 满足 `'static`（`compio-buf-0.8.3/src/io_buf.rs:540` 只给
   `&'static mut B` 实现了 `IoBufMut`）。环的段是借来的 `&mut [MaybeUninit<u8>]`，
   **不能**直接交给设备，因此设备 ↔ 环之间必然多一次 `owned` 缓冲的 memcpy。适配器在
   **段级**仍然零拷贝（段直接进 `move_items_from_input_async` / `move_items_into_output_async`），
   这次拷贝发生在 `abs_buff_compio_adapt` 的 `TrInput` / `TrOutput` 实现内部。
3. **推荐形态**：**BuffRead / BuffWrite 各自 = 「环的一个半部」+「一个后台泵任务」**。
   * 调用方看到的 `TrBuffTryRead` / `TrBuffRead` / `TrBuffTryWrite` / `TrBuffWrite`
     **完全由 ring 的功能承担**——直接委托给 `RingReader` / `RingWriter`，连 future
     类型（`RingReadAsync` / `RingWriteAsync`）都原样复用，不新造一层（§4、§6）；
   * 后台泵只做一件事：在设备与环之间搬段（§6）；
   * `flush` / `close` 用 ring 自己的语义表达，不需要自定义通知原语（§7）。
4. **唯一需要的跨 crate 改动**：`buffex` 的 ring 补上**关闭入口**（`close`）。没有它，
   「设备 EOF/出错」与「调用方要求收尾」都无法唤醒在对端 park 的等待者，适配器只能自己
   造「通知 + select 竞速」一套旁路机制。补上以后，EOF / 收尾全部退化成 ring 的状态语义
   （§5、§9）。这同时兑现 `buffex_tokio_adapt` 笔记 §7 的第一条遗留（「`Ring` 仍缺
   `close`」），将来 tokio 侧也能靠它删掉自己那层 `Drained → Closing` 合成。
5. **`abs_buff_compio_adapt` 只保留设备级一族**（`ReadAsInput` / `WriteAsOutput`，即
   `TrInput` / `TrOutput` 的实现），删掉缓冲级一族（`CompioReadAsBuff` /
   `CompioWriteAsBuff`）。它现在的缓冲级一族**已经编译不过**（见 §3.2），因为
   `abs_buff` `e4092c8` 之后 `TrBuffRead` / `TrBuffWrite` 的关联类型位置变了；顺带这也
   说明「Ring 来做 TrBuffRead / TrBuffWrite」才是与上游同步的形态。

### 2.1 与 `buffex_tokio_adapt` 的差异一览

| 维度 | tokio 版（已落地） | compio 版（本方案） |
| --- | --- | --- |
| 驱动模型 | 按需推进，不 spawn | **内部 spawn 后台泵**（`spawn` 不要求 `Send`） |
| `try_read` | 先同步 `poll_once_` 推一轮搬运 | **不推**，直接委托给 ring |
| 段 ↔ 设备 | 零拷贝（段直连 `TrInput` / `TrOutput`） | 段级零拷贝，但设备级必经一次 owned 中转（compio 约束） |
| EOF 表达 | 适配器自记 `eof_`/`err_`，把 `Drained` 合成 `Closing` | **ring 的 `PRODUCER_CLOSED`**（需给 ring 补 `close`） |
| 收尾 | `flush_async` / `close_async` 自己循环冲 | `flush` 用「等环空」的 demand 技巧；`close` 请求泵排空 + `shutdown` 后 await 任务 |
| 执行体要求 | 无（`join!` 里、同步上下文都能用 `try_*`） | 必须在 compio runtime 线程内（构造时即 spawn） |
| 取消 | `gen_may_cancel_future` 包装各方法 | 对外入口直接复用 ring 的 `RingReadAsync` / `RingWriteAsync`（本身就是 `gen_may_cancel_future` 产物）；新造的 `flush` / `close` 用宏包装 |

| `type ReadAsync<'f> = RingReadAsync<'f,'f,RingBufOf<C>,u8>`，`fn read_async` 直接 `self.rx_.read_async(demand)` | **通过**：`TrBuffRead` / `TrBuffTryRead` 可以只做委托，连 future 类型都不必新造 |
| `type WriteAsync<'f> = RingWriteAsync<'f,'f,RingBufOf<C>,u8>` 同理 | **通过** |

| `impl Unpin for BuffRead/BuffWrite`（环含 `PhantomPinned`，`RingReader`/`RingWriter` 因此 `!Unpin`） | **通过**：与 tokio 版同一处理 |
| `#[abs_buff::gen_may_cancel_future(...)]` 包装 `flush` / `close`，`close` 里 `pump.await`（`JoinHandle<()>`） | **通过** |
| `Demand::at_least(capacity)` 在 `RingWriter` 上可用 | **通过**（语义见 §3.2 的运行期验证） |

**踩到的 rustc 限制（要写进代码注释）**：`spawn` 一个「泛型参数要从投影类型里推断」的
async fn，必须写**显式 turbofish**，否则报

```
error[E0284]: type annotations needed: cannot satisfy `impl Future<Output = ()>: 'static`
```

```rust
// ✗ E0284：S 要从 RingWriter<SharedRingOf<C>, RingBufOf<C>, u8> 里反推
let pump = compio::runtime::spawn(read_pump_(dev, tx, ctl.clone()));
// ✓ 显式给出泛型实参
let pump = compio::runtime::spawn(read_pump_::<R, C, SharedRingOf<C>>(dev, tx, ctl.clone()));
```

最小复现实验的结论（探针 `probe_static.rs` 里逐级放大）：

| 形态 | 结果 |
| --- | --- |
| 泵对 `S` 泛型 + 调用处 `S` 也是泛型参数（`'static` 来自 where 子句） | 通过 |
| 泵对 `S` 泛型 + 调用处给**具体** `SharedOf<C>`，**但需要 rustc 反推**泛型 | **E0284** |
| 同上，但显式 turbofish | 通过 |

即：这不是 `Send` 那类 GAT 问题（tokio 版 §3 的成因），而是「opaque future 的 `'static`
在泛型实参依赖投影/推断时无法被证明」。实现时统一用 turbofish 规避。

* **调用方永远只和 Ring 的语义打交道**：`read_async` 拿 `RingSegmRef`、`write_async`
  拿 `RingSegmMut`，`iter_slices` 只是窥视、`move_items_*` 才推进消费——一行都不用重讲。
* **适配器不实现任何缓冲逻辑**：它只负责「装配 + spawn + 生命周期 + 错误转发」。
* **设备差异全部收敛在 `abs_buff_compio_adapt`**：`buffex_compio_adapt` 只见
  `TrInput` / `TrOutput`，与 tokio 版对称。

## 5. 唯一需要的 `buffex` 改动：环形缓冲的关闭入口

### 5.1 为什么必须有

环的状态字里早有 `PRODUCER_CLOSED` / `CONSUMER_CLOSED` 两个标志，`try_read_internal_` /
`try_write_internal_` 也已经按它们返回 `Closing`（`ring_core_.rs:236`、`:244`、`:270`），
`is_producer_closed` / `is_consumer_closed` 也是公开的——但**没有任何代码把它们置起来**，
也没有任何路径会在「置起来」之后唤醒对端。后果：

| 场景 | 没有 `close` 会怎样 |
| --- | --- |
| 读泵读到设备 EOF，调用方正 park 在 `rx.read_async(demand)` 上等数据 | 环里不会再有 `advance_write`，**没人唤醒消费者**，调用方永久挂住 |
| 写泵写设备出错，调用方正 park 在 `tx.write_async` 上等空间 | 同上，永久挂住；且 `flush` 也等不到 |
| `BuffWrite::close_async` 想让泵「排空后收工」 | 泵 park 在空环上，**没有任何信号能唤醒它**，只能靠取消任务（则丢数据、也不 `shutdown`） |

在适配器里自造一套「通知 + select 竞速」也能绕过（§9 D1），但它要在两个方向各写一个
手搓 race，还要自己合成 `Drained → Closing`——而 `ring` 的状态语义天生就是干这个的。

### 5.2 改动清单（估计 ~30 行 + 测试）

```rust
// buffex/src/ring/ring_core_.rs
impl<B, T> Ring<B, T> where B: BorrowMut<[MaybeUninit<T>]> {
    /// 关闭生产端（EOF）：此后不再有新数据；唤醒等待中的消费者。
    /// 幂等；已关闭时直接返回。
    pub fn close_producer(&self) { self.close_producer_() }
    /// 关闭消费端：此后不再有消费者；唤醒等待中的生产者。
    pub fn close_consumer(&self) { self.close_consumer_() }
}

impl<B, T> Ring<B, T> {
    fn close_producer_(&self) {
        // 只有抢到「置位」的一方负责唤醒；重复 close 直接返回。
        if !self.buf_stat_.try_set_producer_closed_() {
            return;
        }
        // 与 advance_write 同款：先看兴趣位快照，再让 Consumer::wake 在锁内做
        // 「判定 → 认领 → 取走」，唤醒放在锁外。
        if has_flag(self.buf_stat_.value(), CONSUMER_STNDBY) {
            let consumer = unsafe { self.consumer_.as_ref_unchecked() };
            consumer.wake(&self.buf_stat_);
        }
    }
    fn close_consumer_(&self) { /* 对称：try_set_consumer_closed_ + producer.wake */ }
}

impl<S, B, T> RingWriter<S, B, T> { pub fn close(&self) { self.ring_ref_.borrow().close_producer_() } }
impl<S, B, T> RingReader<S, B, T> { pub fn close(&self) { self.ring_ref_.borrow().close_consumer_() } }
```

判定面（**必须与唤醒路径同步改**，否则会漏唤醒）：

```rust
// buffex/src/ring/ring_core_.rs
impl RingState {
    pub(super) fn can_consume_(&self, demand: &Demand<usize>) -> bool {
        // 关闭即「条件永久不可满足」，必须让等待者醒来去拿 Closing。
        self.data_size() >= demand.min().unwrap_or(1) || self.is_producer_closed()
    }
    pub(super) fn can_produce_(&self, demand: &Demand<usize>) -> bool {
        self.free_size() >= demand.min().unwrap_or(1) || self.is_consumer_closed()
    }
    pub(super) fn try_set_producer_closed_(&self) -> bool { /* CAS: !flag → flag */ }
    pub(super) fn try_set_consumer_closed_(&self) -> bool { /* 同上 */ }
}

// buffex/src/ring/half_.rs
impl TrPark for Consumer<T> {
    fn wake(&self, state: &RingState) {
        let Some(reg) = self.ring_half_.take_for_wake_(
            |min| state.data_size() >= min || state.is_producer_closed(),   // ← 新增
            || state.try_claim_consumer_standby_(),
        ) else { return };
        reg.waker_.wake();
    }
}
// Producer::wake 对称：state.free_size() >= min || state.is_consumer_closed()
```

### 5.3 顺带必须修的一处：`try_read_internal_` 的 EOF 例外

该函数的文档已经写明「**EOF 例外**——写端已关闭（不再会有更多数据）时，返回现有部分
（可能不足下限）」，但代码没有兑现：

```rust
if ready < min_len { return Err(ConsumerError::Drained(pos.rp)); }   // ← 关不关都一样
```

补上 `close` 之后这会变成**忙等**：等待者以 `at_least(k)`（k>1）park → `close_producer`
唤醒（`can_consume_` 现在为真）→ `try_read_` 仍返回 `Drained` → 再 park → `can_consume_`
仍为真 → 立刻醒…… 一圈不 await 的紧循环。修法（与文档一致）：

```rust
let eof = has_flag(s, PRODUCER_CLOSED);
if ready < min_len && !eof { return Err(ConsumerError::Drained(pos.rp)); }
let take = core::cmp::min(max_len, ready);
```

影响面：`buffex_tokio_adapt` 的调用方一直用 `at_least(1)`（其测试注释还专门解释了原因），
`k=1` 时 `ready < 1` 等价于 `ready == 0`，走的本来就是「空环 + 已关 → Closing」分支，
因此这个修正**不改变**现有行为，只是让 `k>1` 不再忙等。

### 5.4 关闭之后的语义（要有测试钉住）

| 操作 | 已关生产端（PRODUCER_CLOSED） | 已关消费端（CONSUMER_CLOSED） |
| --- | --- | --- |
| `try_read` / `read_async` | 环里还有数据 → 照常给（可不足下限）；取空 → `ConsumerError::Closing` | `ConsumerError::Closing` |
| `try_write` / `write_async` | `ProducerError::Closing`（写端自己关了） | `ProducerError::Closing` |
| park 中的等待者 | 立即被唤醒并拿到 `Closing` | 立即被唤醒并拿到 `Closing` |
| `is_producer_closed` / `is_consumer_closed` | `true` | `true` |

## 6. 适配器设计

### 6.1 `BuffRead`：设备 → 环

```rust
pub struct BuffRead<R, C = DefaultAllocConfig, S = SharedRingOf<C>>
where
    R: compio::io::AsyncRead + 'static,
    C: TrAllocConfig,
    S: Borrow<Ring<RingBufOf<C>, u8>> + 'static,
{
    ring_: S,                                   // 查 capacity / data_size 用
    rx_: RingReader<S, RingBufOf<C>, u8>,       // 调用方这一侧（= TrBuffRead）
    ctl_: Rc<Ctl_>,                             // 设备错误/结束的暂存（泵写、调用方读）
    pump_: Option<compio::runtime::JoinHandle<()>>,  // Drop 即 cancel
    _dev_: PhantomData<fn() -> R>,              // 设备已移入后台任务
}
```

* `try_new(dev, cap, cfg) -> Result<Self, TryNewError>`：造环 → `Ring::split_unchecked`
  → `spawn(read_pump_)`。**必须在 compio runtime 内调用**（`spawn` 会在 runtime 缺失时
  panic；建议用 `Runtime::try_current()` 先判，返回错误而不是 panic，见 §13 Q2）。
* 对外 trait 实现全是**一行委托**：

```rust
impl<R, C, S> abs_buff::TrBuffTryRead<u8> for BuffRead<R, C, S> { /* … */
    type SegmRef<'f> = RingSegmRef<'f, RingBufOf<C>, u8> where Self: 'f;
    type Err = ConsumerError<usize>;
    fn try_read<'f>(&'f mut self, demand: &'f Demand<usize>) -> SomeOf<Self::SegmRef<'f>, Self::Err> {
        self.rx_.try_read(demand)
    }
}
impl<R, C, S> abs_buff::TrBuffRead<u8> for BuffRead<R, C, S> {
    type ReadAsync<'f> = RingReadAsync<'f, 'f, RingBufOf<C>, u8> where Self: 'f;
    fn read_async<'f>(&'f mut self, demand: &'f Demand<usize>) -> Self::ReadAsync<'f> {
        self.rx_.read_async(demand)          // 取消能力随 ring 的 future 一起拿到
    }
}
```

* 泵（`'static`、非 `Send`）：

```rust
async fn read_pump_<R, C, S>(
    mut dev: R, tx: RingWriter<S, RingBufOf<C>, u8>, ring: S, ctl: Rc<Ctl_>,
) where R: compio::io::AsyncRead + 'static, C: TrAllocConfig,
      S: Borrow<Ring<RingBufOf<C>, u8>> + Clone + 'static,
{
    // 守卫：**独占持有**泵的生产端半部 `tx`。无论正常退出、被取消还是 panic，
    // Drop 时都 `half.close()`（`buffex` 的 close 收 `&mut self`，见 461f10d），
    // 让调用方的 park 一定能醒（拿 Closing）；循环里经 DerefMut 使用这个半部。
    let mut guard = CloseOnDrop_::new_(tx);
    loop {
        let demand = Demand::at_least(1);
        let some = guard.write_async(&demand).await;       // 环满 → park 等消费
        let Some(mut segm) = some.pick_left() else { break };   // 消费端关了
        let room = segm.least_count();
        let moved = {
            let mut input = ReadAsInput::new(&mut dev);
            segm.move_items_from_input_async(&mut input, &Demand::no_more_than(room)).await
        };
        drop(segm);                                        // 提交：唤醒消费者
        match moved.into_inner() {
            SomeLR::Left(n) => debug_assert!(n > 0),
            SomeLR::Right(err) | SomeLR::Both(_, err) => { ctl.set_read_err_(err); break }
        }
    }
}
```

  * 与 tokio 版 `pump_` 的循环体**逐行同构**，区别只有两点：这里不因「环满」而 return
    （park 由 ring 负责），以及设备结束/出错后由守卫 `close` 而不是记内部 `eof_`。
  * EOF 的翻译在 `ReadAsInput` 里（`Ok(0)` → 带 `Closing` 标签的错误，见 §8）；
    泵只需要把 `Closing` 当成「正常结束」而不是设备错误。
  * 泵在等设备读的整个过程中**握着写段**（段未 drop ⇒ 空间未提交给消费者）。这不是
    死锁（消费者总能取走已提交的部分），只是把「一格预留空间」当作读缓冲用；换来的是
    与 tokio 版一致的简单循环。

### 6.2 `BuffWrite`：环 → 设备

```rust
pub struct BuffWrite<W, C = DefaultAllocConfig, S = SharedRingOf<C>> {
    ring_: S,
    tx_: RingWriter<S, RingBufOf<C>, u8>,       // 调用方这一侧（= TrBuffWrite）
    ctl_: Rc<Ctl_>,
    pump_: Option<JoinHandle<()>>,
    _dev_: PhantomData<fn() -> W>,
}
```

* 委托同 `BuffRead`（`SegmMut = RingSegmMut<'f, RingBufOf<C>, u8>`、
  `WriteAsync = RingWriteAsync<'f,'f,RingBufOf<C>,u8>`）。
* 泵：

```rust
async fn write_pump_<W, C, S>(
    mut dev: W, rx: RingReader<S, RingBufOf<C>, u8>, ring: S, ctl: Rc<Ctl_>,
) where S: Borrow<Ring<RingBufOf<C>, u8>> + Clone + 'static {
    // 守卫同上：独占持有泵的消费端半部，Drop ⇒ `half.close()`，让调用方随后拿到 Closing。
    let mut guard = CloseOnDrop_::new_(rx);
    loop {
        let demand = Demand::at_least(1);
        let some = guard.read_async(&demand).await;      // 环空 → park 等数据
        let Some(mut segm) = some.pick_left() else { break };   // 生产端关了（close_async）
        let moved = {
            let mut output = WriteAsOutput::new(&mut dev);
            // 段握在这里：设备收下多少，段的 offset 才推进多少；
            // 真正的提交（advance_read）发生在 segm drop。
            segm.move_items_into_output_async(&mut output, &Demand::at_least(1)).await
        };
        drop(segm);
        match moved.into_inner() {
            SomeLR::Left(_) => {}
            SomeLR::Right(err) | SomeLR::Both(_, err) => { ctl.set_write_err_(err); break }
        }
    }
    if ctl.write_err_.borrow().is_none() {
        let _ = dev.shutdown().await;                    // 只有正常收尾才 shutdown
    }
}
```

* **关键不变式**：泵从借出读段到设备写完之间**不 drop 段**。因此
  `ring.data_size() == 0` ⟺「调用方写进环的字节已经全部被设备收下」——`flush` 直接建立
  在这条判据上（§7.1）。
* 消费端守卫的意义：泵因设备错误、panic 或被取消而退出时，一定把
  `CONSUMER_CLOSED` 置上，调用方随后的 `try_write` / `write_async` / `flush` 会拿到
  `Closing`，而不是在一个没人消费的环上无限 park。
* `dev.shutdown()` 只在「生产端已关（`close_async` 正常收尾）」时执行；设备错误退出时
  不 shutdown（避免在坏设备上再发一次系统调用）。

### 6.3 生命周期与取消

| 事件 | 行为 |
| --- | --- |
| 适配器 `drop` | `JoinHandle::drop` ⇒ `task.cancel(true)`：泵被取消，其持有的环半部/设备释放。两侧的 `CloseOnDrop_` 守卫仍会关闭自己那一端（此时无人等待，幂等且无害） |
| 调用方 drop `read_async()` / `write_async()` 的 future | ring 的 park future 自身实现了 `Drop`：`registered_` 为真时撤回登记并释放兴趣位（见 `buffex/dev-notes/ring-20261001-0342.md` §2/§3），无需适配器介入 |
| 泵 panic | 守卫在 unwinding 里关闭半部 ⇒ 调用方拿到 `Closing` 而非挂死；`JoinHandle` 侧报 `JoinError::Panicked`，`close_async` 把它映射成 `Closing`（拟提供 `take_pump_error()` 供排查） |
| 设备 EOF（read 向） | 泵在 `ctl_.read_err_` 里记下结束原因（`Closing` 标签**不**算设备错误，供 `take_error` 过滤）→ 守卫关闭生产端半部 → 消费者取空环后拿到 `Closing` |
| 设备出错（read 向） | 同上，但 `ctl_.read_err_` 里留下真实 `io::Error`，调用方 `take_error()` 取回 |
| 设备出错（write 向） | 泵记错 → 守卫关闭消费端半部 → 调用方 `write_async` / `flush` 拿到 `Closing`，`take_error()` 取回详情 |
| `close_async` | `tx.close()`（置 `PRODUCER_CLOSED` 并唤醒泵）→ `pump_.take()?.await`（泵排空 → `shutdown` → 退出）→ 有设备错误则 `Closing` |

### 6.4 `shared_.rs` 里的共用件

* `Ctl_`：设备错误暂存。单线程（compio runtime 是 thread-local）⇒ 用
  `Rc<RefCell<Option<(io::Error, ReadErrTag / WriteErrTag)>>>` 即可，**不需要原子**；
  `take_error()` 取走即清空，与 tokio 版同形。
* `CloseOnDrop_<H>`：`{ half_: H }`（`H: TrCloseHalf_`，即 `RingWriter` 或 `RingReader`），
  `Drop` 里调 `half_.close_half_()` —— 即半部自己的 `close`。它**独占持有泵那一份半部**：
  `buffex` `461f10d` 把 `close` 收紧为 `&mut self` 之后，共享容器（`Shared` 只有 `Borrow`）
  已无法提供 `&mut Ring`，而守卫本就该是关闭权的所有者。半部自身没有 `Drop`，所以守卫是
  泵退出时唯一的关闭者。
* `alloc_ring_(cap, &cfg)`：用 `C::RingBodyAlloc` 造 `Owned<[MaybeUninit<u8>], _>`、
  经 `Ring::try_new` 校验容量、再用 `C::RingSharedAlloc` 装进 `Shared`。
* `split_ring_(ring)`：`unsafe { Ring::split_unchecked(ring) }` 的安全封装——容器是**本
  crate 刚创建**的 `Shared`、不存在第二句柄、拆分只发生一次（与 tokio 版同一论证）。
* `TryNewError { InvalidCapacity(usize), NotInRuntime }`：`Display` + `core::error::Error`。

## 7. `flush` / `close` 的语义与实现

### 7.1 `flush_async`：用「等整环空出来」表达「等设备收完」

```rust
#[abs_buff::gen_may_cancel_future(BuffWriteFlush, pub, new(pub(crate)))]
async fn buff_write_flush_async_<'f, W, C, S, K>(me: &'f mut BuffWrite<W, C, S>, cancel: K)
    -> Result<(), ProducerError<usize>>
where /* … */ K: abs_cancel::TrCancellationToken
{
    let cap = me.ring_.borrow().capacity();
    let demand = Demand::at_least(cap);          // ← 只在 free == cap（即 data_size == 0）时成功
    loop {
        if cancel.is_cancelled() { return Err(ProducerError::Cancelled) }
        match me.tx_.try_write(&demand).into_inner() {
            SomeLR::Left(segm) => { drop(segm); return Ok(()) }      // 借到即丢，提交 0 字节
            SomeLR::Right(ProducerError::Stuffed(_)) => {}
            SomeLR::Right(err) => return Err(err),                   // Closing（消费端已关）等
            SomeLR::Both(_, err) => return Err(err),
        }
        let some = me.tx_.write_async(&demand)
            .may_cancel_with(cancel.child_token()).await;            // park：泵 advance_read 时唤醒
        /* 同上 match */
    }
}
```

* 为什么成立：`try_write_internal_` 的下限判定是 `free_size >= min`（`ring_core_.rs:276`），
  取 `min = capacity` 就等价于 `data_size == 0`；而 §6.2 的不变式保证那一刻「数据已全部
  被设备收下」。预算里 `at_least(cap)` 不会触发 `min_len > cap → Unsatisfiable`
  （相等是允许的）。运行期探针已验证（§3.2）。
* 为什么不需要自定义通知：park/唤醒复用 ring 现成的**生产者等待槽**，
  `advance_read`（段 drop）本来就会在 `PRODUCER_STNDBY` 时唤醒生产者。
* 「借到就丢」提交 0 字节 ⇒ `advance_write(0)`：位置不变，只会顺手唤醒一下（无害）。

### 7.2 `close_async`

```rust
#[abs_buff::gen_may_cancel_future(BuffWriteClose, pub, new(pub(crate)))]
async fn buff_write_close_async_<'f, W, C, S, K>(me: &'f mut BuffWrite<W, C, S>, _cancel: K)
    -> Result<(), ProducerError<usize>>
{
    me.tx_.close();                        // ① 不再有新数据；唤醒 park 中的泵
    if let Some(pump) = me.pump_.take() {  // ② 等泵排空剩余数据 + shutdown + 退出
        let _ = pump.await;                //    （JoinHandle 只能 poll 一次 ⇒ 必须 take）
    }
    if me.ctl_.write_err_.borrow().is_some() { return Err(ProducerError::Closing) }
    Ok(())
}
```

* 排空是**泵自己的循环**完成的：`tx.close()` 之后，泵 `read_async` 会先取走环里剩余数据
  （`ready > 0` 时照常给段），取空后才拿到 `Closing` 并进入收尾。
* 调用方在 `close_async` 期间不可能再写入（`&mut self`），因此不存在「关完又提交」的丢数据窗口。
* 之后再 `try_write` / `flush_async`：ring 返回 `ProducerError::Closing`，语义自洽。
* `close_async` 幂等（`pump_` 被 take 成 `None`，第二次直接看错误槽返回）。

### 7.3 与 tokio 版语义的对照

| 项 | tokio 版 | compio 版 |
| --- | --- | --- |
| `flush_async` 保证 | 环内已提交数据全部送达设备 | 同（由 §6.2 不变式 + `at_least(cap)` 判据） |
| `close_async` 保证 | 冲净 + `shutdown` | 冲净 + `shutdown`（由泵执行）+ 等泵退出 |
| `take_error` | `(io::Error, ReadErrTag / WriteErrTag)` | 同（存在 `Rc<RefCell<…>>` 里，泵写、适配器取） |
| 忘记 `flush` 的后果 | 数据留在环里 | 同（泵会继续在后台搬，但「已送达」不受保证；`close_async` 会兜底） |

## 8. `abs_buff_compio_adapt` 的取舍

### 8.1 保留：设备级 `ReadAsInput` / `WriteAsOutput`

`buffex_compio_adapt` 的泵与它们对接（`TrInput` / `TrOutput`），因此这一族必须留。
其中 `ReadAsInput` **现在违反 `abs_buff` 的输入搬移契约**，必须照 tokio 版的修法补齐：

```rust
// 现在（read_as_input.rs）：设备 EOF 时返回裸的 Left(0)
Result::Ok(n) => SomeOf::new_left(n),
// 应当（与 abs_buff_tokio_adapt 的修复逐行对应）
Result::Ok(0) => SomeOf::new_right(TaggedError::new(
    std::io::Error::from(std::io::ErrorKind::UnexpectedEof),
    ReadErrTag::Closing,        // 终止性标签：段级搬移据此收尾
)),
Result::Ok(n) => SomeOf::new_left(n),
```

理由：`segm_mut_input_async_` 里有 `assert!(*cc > 0 || x.contains_right())`
（`abs_buff/src/buffer/segm_.rs:915`），而 compio 的 `read` 用 `Ok(0)` 表示 EOF——
不翻译就会在泵里 panic。`target.is_empty()` 分支同样不应返回裸 `Left(0)`（改成带
`Closing` 的错误即可，实际不会被触发）。

`WriteAsOutput` 方向不需要改（`Ok(0)` 在 `AsyncWrite` 里合法）；仅记一条风险：
`move_items_into_output_async_` 在设备持续返回 `Left(0)` 时会 `continue` 空转
（`segm_.rs:1030`），真实设备不会这样返回，测试用的假设备要避免。

### 8.2 删除：缓冲级 `CompioReadAsBuff` / `CompioWriteAsBuff`

* 它们已经**编译不过**（§3.2），语义上也不再需要：`TrBuffRead` / `TrBuffWrite` 由
  `buffex` 的 ring 承担才是不重复实现缓冲逻辑的形态；
* 连带删除：`src/read_as_buff.rs`、`src/write_as_buff.rs`、`lib.rs` 的模块声明与
  重导出、crate 文档里「第 2 组：缓冲级」一节、`tests/compio_adapt.rs` 里针对它们的用例；
* 它们内部的 `SegmRef` / `SegmMut` + `SegmReclaim` 手写游标方案随之作废（这正是「自己
  造缓冲」的代价：与 `abs_buff` 的 trait 形状同步一次就坏一次）。

## 9. 备选方案与取舍

| 方案 | 内容 | 取舍 |
| --- | --- | --- |
| **D2（推荐，本方案）** | 给 `buffex::ring` 补 `close`，适配器完全委托 ring | 需要改 `buffex` 公开 API（+2 个 trait 外方法、2 个半部方法，1 处判定与 2 处唤醒谓词、1 处 `try_read_internal_` 修正）；换来的是一整套「不用自己发明同步原语」的适配器；顺带兑现 tokio 侧遗留 |

| V-B | 泵直接用 compio 设备 API，自己维护可复用 `owned` 缓冲 + `move_items_from_buff` / `move_items_to_buff` | 稳态零分配；但要在本 crate 里重写一遍「设备 ↔ owned 缓冲」，并自己处理 EOF 翻译，与「设备差异收敛在 abs_buff_compio_adapt」的分层相悖 |
| 不 spawn（tokio 同款按需驱动） | 不适用：compio 没有「同步 poll 一次设备操作」的入口，`try_read` 里推不动一轮（completion IO 必须经过 runtime 的 driver），硬要做得把 driver 拉进来 | 排除 |

可以叠加的优化：给 `ReadAsInput` / `WriteAsOutput` 增加「复用 owned 缓冲」的 owned 变体，
把 V-A 的那次 `Vec` **分配**也省掉（拷贝仍在）。该项已按 Q5 一起落地，设计见 §13.1。

## 10. 公开 API 草案（§13 已确认，Q5 的增量见 §13.1）

### 10.1 `buffex`（唯一的上游增量）

```rust
impl<B, T> Ring<B, T> where B: BorrowMut<[MaybeUninit<T>]> {
    pub fn close_producer(&self);   // 幂等
    pub fn close_consumer(&self);   // 幂等
}
impl<S, B, T> RingWriter<S, B, T> { pub fn close(&self); }   // = close_producer
impl<S, B, T> RingReader<S, B, T> { pub fn close(&self); }   // = close_consumer
```

## 12. 风险与遗留

1. **一次额外的 memcpy 无法消除**（compio 的 buffer-by-value + `'static` 约束）。缓解手段
   只有「复用 owned 缓冲、不再每次分配」（§13.1）与「选择更少的设备 IO 次数」。
2. **`spawn` 需要 runtime 上下文**：`try_new` 必须在 `block_on` 内调用；适配器也不能跨
   runtime/线程移动（类型 `!Send` 已经保证了后者）。文档必须显眼说明。
3. **E0284 turbofish 限制**（§3.1）：实现时所有 spawn 调用点都要写显式泛型实参，并在
   注释里写明原因，避免后人「顺手简化」后编译不过。
4. **泵 panic 的可见性**：守卫保证对端不挂死，但 `JoinError::Panicked` 只有 `close_async`
   能看到；若调用方从不 close，panic 会被静默。拟提供 `take_pump_error()`。
5. **取消的语义**：drop 适配器会取消泵，此时若设备写已提交到内核但未收到完成通知，
   「设备侧已生效、环侧未记账」是 compio 完成式 IO 的固有取消语义，无法在适配器层修复。
6. **`buffex` 的 `close` 是新公开 API**：已按 AGENTS.md 纪律 1 取得同意（§13 Q1）；它的
   §5.2/§5.3 改动仍应在 `buffex` 自己的 dev-notes 里单独留档（可复用本节的因果链）。
7. `buffex_tokio_adapt` 将来可以借 `close` 删掉自造的 EOF 合成（本方案不改它，避免把
   两个 crate 的改动耦合在一轮里）。
8. `abs_buff_compio_adapt` 的未提交改动已定为「先提交留档，再删改」（§13 Q4）；在提交完成前
   不得编辑该 crate 的代码文件。

### 13.1 Q5 的落地设计：owned 变体的设备适配

动机：`ReadAsInput` / `WriteAsOutput` 现在每次设备 IO 都 `vec![0u8; n]`（§2 表、§8.1）。
泵是长期存在的，缓冲可以随泵一起复用，把「每次 IO 一次分配」降为「每泵一次分配」。

```rust
// abs_buff_compio_adapt/src/read_as_input.rs（新增，不改动现有的借用版）
/// 拥有设备与中转缓冲的 `TrInput<u8>` 实现：稳态下不再分配。
pub struct ReadAsInputOwned<R> {
    dev_: R,
    /// 复用中转缓冲；容量按环容量预留一次即可。
    stage_: Vec<u8>,
}
impl<R: compio::io::AsyncRead> ReadAsInputOwned<R> {
    pub fn new(dev: R) -> Self;                       // stage_ 初始为空
    pub fn with_capacity(dev: R, cap: usize) -> Self;  // 预留 cap 字节
    pub fn into_inner(self) -> R;
    pub fn stage_capacity(&self) -> usize;
}
impl<R: compio::io::AsyncRead> abs_buff::io::TrInput<u8> for ReadAsInputOwned<R> {
    type ReadAsync<'f> = ReadAsInputOwnedAsync<'f, 'f, R> where Self: 'f, u8: 'f;
    type Err = TaggedError<std::io::Error, ReadErrTag>;
    // 语义与借用版逐行一致（含 Ok(0) → Closing 的 EOF 翻译）；差别只有：
    //   let buf = core::mem::take(&mut self.stage_);   // 容量留在 buf 上
    //   buf.resize(target.len(), 0);
    //   let BufResult(res, buf) = self.dev_.read(buf).await;
    //   self.stage_ = buf;                             // 归还（可能已扩容）
    //   把前 n 字节拷回 target
}

/// 对称的 `TrOutput<u8>` 实现。
pub struct WriteAsOutputOwned<W> { dev_: W, stage_: Vec<u8> }
```

要点与约束：

1. **不替换现有类型**：`ReadAsInput<'a, R>` / `WriteAsOutput<'a, W>`（借用设备、内部临时
   分配）保持原样，供「只想快速借用一下」的调用方使用；owned 变体是新增项，`mod.rs`
   逐项导出（AGENTS.md 纪律 5：不用 `*`）。
2. `Vec<u8>` 的 `IoBufMut` 由 compio 提供（`compio-buf-0.8.3/src/io_buf.rs:570`），
   `read` 会把 `SetLen` 更新成实际读到的字节数并按值归还，因此「取走 → 读 → 放回」
   不会丢容量；若 `reserve` 触发了扩容，归还的 `Vec` 也已带上新容量。
3. 每个泵各持一个 owned 变体（read 泵 `ReadAsInputOwned::with_capacity(dev, ring_cap)`，
   write 泵 `WriteAsOutputOwned::with_capacity(dev, ring_cap)`），因此**泵内不再有任何
   分配**：`allocator_config_applies_per_allocation_site_` 用例可以断言「跑完一圈，
   两个记账分配器的计数都不再增长」。
4. 仍然**不改变**「设备 ↔ 环之间一次 memcpy」这一事实：`stage_` 就是那次中转；Q5 省的
   是**分配**，不是拷贝（拷贝由 compio 的 buffer-by-value 契约决定，见 §1.2）。
5. 文档（`///`）要写明：owned 变体把缓冲生命周期与设备绑定，适合长期持有（泵）；
   短生命周期场景用借用版更省内存。

## 14. 追加调研（人类提问）：给 `Ring` 的 `B` 加 `IoBufMut` 约束，能不能从环里直接切走、去掉中转缓冲？

**问题**：既然 compio 要求 `IoBufMut`，能不能让 `buffex::ring` 的缓冲本体 `B` 直接满足
`IoBufMut`（配上相应 API），于是设备直接读写环内窗口，彻底删掉 §13.1 那层 owned 中转？

### 14.1 结论

* 「**给 `B` 加 `IoBufMut` 约束**」这条路**不成立**：`B` 是整个环体，而设备要的是
  「在写位置开始的一段窗口」；环体满足 `IoBufMut` 既非必要也不充分（§14.2）。
* 但问题背后的目标——**零拷贝直达**——**是可行的**，只是机制不同：在**适配器**里造一个
  `'static` 的「环窗口」类型（持有 `Shared<Ring>` 克隆 + 裸指针 + 长度，实现
  `IoBuf` / `IoBufMut` / `SetLen`），再让 `buffex` 补一个**原始预留 + 外部提交**入口
  （§14.3、§14.5）。
* 安全性有明确的机制支撑，不是「靠 `'static` 蒙过去」：compio 在提交时把 op（含用户
  buffer）的强引用**泄漏给 driver**，只有收割 completion 时才释放（§14.4）。因此窗口
  类型只要**拥有环的强引用**，设备操作的迟到写入就一定落在有效内存上。
* 代价：新增 `unsafe` 面（裸指针构造 + 两处安全注释）、`buffex` 再增一族公开 API、
  跨末端要拆两次操作、取消语义要在文档里写清（§14.6）。据此建议**分两阶段**落地
  （§14.7）。

### 14.2 为什么「给 `B` 加 `IoBufMut` 约束」不行

| 事实 | 后果 |
| --- | --- |
| compio 的读操作**从 `as_uninit()` 的起始地址**开始写（`compio-driver/src/sys/op/general/poll.rs:99`、`sys_sys_slice.rs:118`），写操作只取 `IoBuf::as_init()` 的 **`[0, buf_len())`** | 只能把「窗口的起点」交给设备。把整个环体交出去 = 从环体第 0 字节开始覆盖，与 `wp`/`rp` 无关，直接破坏未消费数据 |
| 环的位置是 `rp`/`wp` 两个会绕回的物理索引（`IoPos`），窗口是 `[wp, wp+take)` 这样一段**子区间**，还可能要跨末端拆两段 | `B: IoBufMut` 描述的是「整块缓冲」，与「任意子区间」不是一回事 |
| `IoBuf: 'static`（`compio-buf/src/io_buf.rs:10`）是**类型**上的约束：实现类型不能带生命周期参数 | 直接从环段借一个 `&mut [MaybeUninit<u8>]`（带生命周期）**永远**不满足；必须是「裸指针 + 拥有所有权」的自持类型 |
| 段已被 `try_write` 借出后，环的写位置**还没推进**；设备写了多少要由「外部写入量」提交 | `ReclSliceMut` 的提交量只由段自己的搬移助手推进（`offset_`），**没有外部提交入口**（`buffex/src/ring/reclaim.rs:304`、`:255`），raw 路径必须补 API |

### 14.3 可行的形态：环窗口（零拷贝）

```rust
// buffex_compio_adapt/src/window_.rs（新增；S 是环容器，clone 一份用于保活）
/// 指向环内一段**未提交**可写区的 `'static` 窗口：可直接交给 compio 的读操作。
pub struct RingWriteWindow<S, B>
where S: Borrow<Ring<B, u8>> + 'static, B: BorrowMut<[MaybeUninit<u8>]> + 'static,
{
    ring_: S,                       // 保活：设备操作可能在本任务被取消之后才完成
    ptr_: NonNull<MaybeUninit<u8>>,
    cap_: usize,
    len_: usize,                    // 已被设备写入/初始化的字节数（由 set_len 更新）
}

impl<S, B> compio::buf::IoBuf for RingWriteWindow<S, B> {
    fn as_init(&self) -> &[u8] { /* 前 len_ 字节；len_ == 0 时是空切片 */ }
}
impl<S, B> compio::buf::IoBufMut for RingWriteWindow<S, B> {
    fn as_uninit(&mut self) -> &mut [MaybeUninit<u8>] { /* ptr_ .. ptr_+cap_ */ }
}
impl<S, B> compio::buf::SetLen for RingWriteWindow<S, B> {
    unsafe fn set_len(&mut self, len: usize) { debug_assert!(len <= self.cap_); self.len_ = len }
}

/// 对称：环内一段**已提交**可读区，只实现 `IoBuf`（设备只读）。
pub struct RingReadWindow<S, B> { ring_: S, ptr_: NonNull<u8>, len_: usize }
```

泵里的用法（对比 §6.1 的中转版本，少了一层拷贝与一次分配）：

```rust
// 读向（设备 → 环）：kernel 直接写进环的预留区
let resv = match tx.reserve_raw(&Demand::at_least(1)).pick_left() {
    Some(r) => r, None => break,
};
let window = RingWriteWindow::new(ring.clone(), resv.as_ptr(), resv.len());
let compio::buf::BufResult(res, window) = dev.read(window).await;
match res {
    Ok(n) => resv.commit(n),                 // = advance_write(n)：仅此刻消费者才可见
    Err(e) => { ctl.set_read_err_(e.into()); break }
}
```

```rust
// 出向（环 → 设备）：设备直接读环里已提交的字节
let resv = match rx.peek_raw(&Demand::at_least(1)).pick_left() { Some(r) => r, None => break };
let window = RingReadWindow::new(ring.clone(), resv.as_ptr(), resv.len());
let compio::buf::BufResult(res, window) = dev.write(window).await;
match res { Ok(n) => resv.consume(n), Err(e) => { ctl.set_write_err_(e.into()); break } }
```

要点：

1. **提交即可见**：设备写入的是尚未提交的预留区，`commit` 之前消费者看不到（`rp`/`wp`
   不变），因此窗口期间不会有任何 `&mut` 别名冲突；`commit` 之后才 `advance_write` 唤醒消费者。
2. **跨末端**：先只支持「不跨末端的连续区」（`take = min(take, capacity - wp)`），尾部由
   下一次预留接上；比上 `IoVectoredBufMut` 简单得多，且 `read_vectored` 的默认实现本来
   也只填第一个非空缓冲。
3. **初始化契约**：`commit(n)` 等于向 ring 断言「这 n 个字节已初始化」；这正是 compio
   在 `advance_to(n)` 里通过 `SetLen::set_len` 交出来的信息。
4. `IoBuf` / `IoBufMut` / `SetLen` 都是**安全 trait**（只有 `set_len` 是 `unsafe fn`），
   所以这里没有 `unsafe impl`；`unsafe` 只出现在 `as_uninit` 内部由裸指针重建切片，
   以及 `set_len` 的契约注释上（AGENTS.md 纪律 7 要求逐条论证）。

### 14.4 为什么 `'static` 在这套机制下是**可满足**的（compio 侧证据链）

`IoBuf: 'static` 的用意是：**设备操作的完成可能晚于发起它的 future 被丢弃**，所以 buffer
所指的内存必须在整个 op 生命周期内有效。compio 的实现确实是这样做的：

| 证据 | 说明 |
| --- | --- |
| `compio-driver/src/sys/driver/iour/mod.rs:343`：`push_raw_with_key` 里注释「if push failed, do not leak the key」+ `key.into_raw()` | 提交成功后**泄漏**那份强引用：`RawOp`（内含 `OpCode` → 内含用户 buffer）在 driver 里一直活着 |
| `compio-driver/src/key.rs:366` `unsafe fn freeze` + `sys/driver/iocp/mod.rs:129` 等 | 阻塞回退路径同样把 key「冻结」后交给 worker 线程 |
| `compio-driver/src/lib.rs:203` `Proactor::cancel` 文档：「The cancellation is not reliable. The underlying operation may continue, but just don't return from `Proactor::poll`」 | 取消只是「不返回结果」；内核**可能**继续写这块内存 |
| `compio-driver/src/lib.rs:203` 的 `Key` 引用计数（`ThinCell`，有 `WeakKey`/`ErasedKey`） | op 与其 buffer 只在 completion 被收割时才 drop |

结论：只要窗口类型**自己**持有一份 `Shared<Ring<…>>` 克隆，环体（及其缓冲本体）在
「op 未完成 / 已取消但 completion 未收割」期间就一定不会释放；即使泵任务被取消、适配器
被 drop，内存也只是**延后释放**，不会出现 use-after-free。这正是 raw 路径能安全成立的
原因，也解释了为什么它必须是一个 `'static` 的自持类型而不是借用型。

顺带把「迟到写入」的语义讲清楚（要写进类型文档）：

* 迟到写入只会落在**已无人认领**的预留区。泵是唯一的写端，而泵被取消后不会再提交任何
  窗口，因此这 n 个字节**永远**不会被 `commit`，也永远不会被消费者看到（`wp` 不动）。
* 消费侧同理：`peek_raw` 让设备读的是**已提交**区间；即使取消后设备才完成读取，读到的
  是环里仍然有效的内容，不存在 torn read（写端要复用该区域必须先 `advance_read`，而
  `advance_read` 只在 `consume` 里发生）。

### 14.5 需要的 `buffex` 增量（raw 预留 + 外部提交）

```rust
// buffex/src/ring/ring_core_.rs（+ mod.rs 逐项导出）
/// 一段「原始写预留」：把连续可写区交给外部设备，由外部按实际写入量提交。
pub struct RawWriteReservation<'f, B, T> { ring_: &'f Ring<B, T>, ptr_: NonNull<MaybeUninit<T>>, len_: usize }
impl<...> RawWriteReservation<'_, B, T> {
    pub fn as_ptr(&self) -> NonNull<MaybeUninit<T>>;
    pub fn len(&self) -> usize;
    /// 提交 `amount <= len()`：推进写位置并唤醒消费者（消费 self，保证恰好一次）。
    pub fn commit(self, amount: usize);
}
/// 对称：已提交可读区 + `consume(amount)`（推进读位置并唤醒生产者）。
pub struct RawReadReservation<'f, B, T> { .. }

impl<S, B, T> RingWriter<S, B, T> { pub fn reserve_raw<'f>(&'f mut self, d: &Demand<usize>) -> SomeOf<RawWriteReservation<'f, B, T>, ProducerError<usize>>; }
impl<S, B, T> RingReader<S, B, T> { pub fn peek_raw<'f>(&'f mut self, d: &Demand<usize>) -> SomeOf<RawReadReservation<'f, B, T>, ConsumerError<usize>>; }
```

* 这里**不做段**：`reserve_raw` 直接由 `buf_cell_`（`UnsafeCell`）算出指针，**全程不创建
  `&mut` 到该区间**。这正是与「用 `iter_slices_mut()` 拿 `&mut` 再转裸指针」的关键区别：
  后者把设备写入放到一个「父 `&mut` 仍然存活」的别名场景里，Stacked/Tree Borrows 下
  是很难论证的（父引用一旦被重新借用就可能让子指针失效），属于应当避免的写法。
* 预留区与「已提交区」（消费者可见）永不相交；预留期间消费者看不到它，因此 SPSC 前提
  不破。
* 备选（不推荐）：给 `ReclSliceMut` 加 `commit_external(amount)` + 从 `iter_slices_mut()`
  取裸指针。API 更少，但引入了上面那条别名论证，且 `ReclSliceMut` 是 `abs_buff` 语义的
  段类型，往里塞「外部提交」会让它的不变量变模糊。

### 14.6 收益、代价与风险

**收益**：读向「kernel → 环」直达、写向「环 → kernel」直达，整条管线**零拷贝**
（这正是 `buffex` 的原始设计意图）；顺带没有每次设备 IO 的 `Vec` 分配与两次额外 memcpy。

**代价**：

1. `unsafe` 面：窗口类型的 `as_uninit`（裸指针重建切片）、`set_len`（初始化契约）各需
   详细安全注释；`buffex` 侧预留/提交要保证「恰好一次、不越界、不重叠」。
2. `buffex` 公开 API 再涨一族（2 个类型 + 2 个半部方法 + 2 个提交方法），需要单独同意
   （AGENTS.md 纪律 1）与单测。
3. 跨末端要拆两次操作（或上 vectored）；每次设备 IO 的长度上限受「到末端为止」的剩余
   空间限制，短读/短写路径比中转版本更多。
4. 取消语义：迟到写入/迟到读取**不会**破坏数据（§14.4），但「设备侧已生效、环侧未提交」
   导致的重发/去重歧义与 §12.5 同源，无法在适配器层消除。
5. `IoBuf`/`IoBufMut` 的契约是**安全 trait + 不安全义务**，编译器不会帮我们兜底；必须靠
   类型不变量（持有 `Shared`、固定分配不搬移、`NonNull` 由 `buf_cell_` 派生）来保证。
6. 需要 Miri（Tree Borrows）与「取消后迟到完成」的专项测试，否则这类代码的回归很难被
   普通用例发现。
